# Swarm Studio: design

A desktop app, in the spirit of Google Antigravity, on top of the `swarm` harness. You
describe an app in a chat. A local "chief" model plans it as small features, and you approve
or comment on the plan. The local worker model then builds each feature through the harness,
while you watch the plan, the task list, live logs, diffs and a live preview.

Started with `uv run swarm studio [PROJECT]` (branch `studio`).

## Owner's decisions (2026-11-01)

| Question | Decision | Why |
|---|---|---|
| Who plans? | **Local qwen2.5-coder:14b, strict JSON plan.** The planner is pluggable (`Planner` protocol); a cloud chief can be added later. | The repo is a fallback for when Claude limits run out. It's the worker's model too, so the GPU never swaps models. |
| What form? | **Desktop app**: a native window (pywebview on the WebView2 runtime built into Windows 11), else an Edge app-mode window. The backend is stdlib Python. | Small downloads: about 1.2 MB for pywebview, or nothing with Edge. Electron and Tauri are 100 MB to several GB. |
| First demo? | **A tiny todo list.** | Small, stateful and obviously checkable in a preview. |

## The rule that shapes everything

ChatBook showed that the 14B writes correct code from an **exact spec**, for **one file of
about 120 lines**, against a **protected frame**, with **hidden tests** and machine
feedback. There, a strong planner (Claude) wrote all of that. Here the planner is the same
14B, so its job is made small and checkable:

1. **A fixed frame** (`frames/webapp`) does everything that crosses features:
   - the HTTP server;
   - route discovery;
   - an in-memory store with predictable ids;
   - request helpers that raise the right 400 or 404 themselves;
   - a page shell that renders UI *sections* declared in `ui.json`.
2. **The chief only fills a JSON plan**, and Ollama forces the reply to a schema:
   - features, each with 1 to 4 routes;
   - per route: what it does, the body, the reply and the errors;
   - the page sections;
   - per feature, 1 to 5 example *scenarios* (requests with expected replies).
3. **Everything the worker gets is generated by plain code** (`swarm/studio/plan.py`):
   - a stub `handler.py` whose CONTRACT docstring is the spec;
   - `task.toml`, with the prompt, the `scope` and the files;
   - the **hidden acceptance tests**, rendered from the scenarios. The model writes data,
     never test code.
4. **Plain code checks the plan** (`plan.problems`):
   - names, paths and route clashes;
   - page actions that point to no route;
   - scenario steps that call a route that doesn't exist yet;
   - `{id}` left in a path;
   - statuses that aren't HTTP statuses.

   The chief gets one retry with the list. Then the owner sees what is left, and **Approve
   stays disabled until it is empty**.
5. **The owner approves the plan.** The first scenario per feature is shown to the worker as
   the worked example; the rest stay hidden from it, but not from the owner.

## The chief loop

```
chat request
  -> chief: outline (1 call) + scenarios (1 call per feature) -> checks -> plan artifact
  -> owner: approve, or comment (the chief revises; unchanged features keep their scenarios)
  -> apply: stubs + ui.json + CONTRACT snapshots committed on the app's main, gates must pass,
            one harness task per feature, hidden tests outside the repo
  -> per task, in order: runner.run_task (worktree, baseline, worker attempts, autofix,
            guard, gates, hidden tests, feedback; up to 4 attempts)
       pass -> review: dispatch.integrate (every gate + every accepted task's hidden tests
               on the merge) -> main fast-forwards -> the preview restarts
       fail -> the build pauses; the owner retries (the model's answers vary) or skips
  -> more chat after the build: the chief plans additions on top of the built features
```

Tasks run one at a time, because a later feature's scenarios may use an earlier feature's
routes. One job thread runs every model call, chief and worker alike, so the single GPU
is never shared.

## What is reused, what is new

- **Reused unchanged:** `runner.run_task`, `dispatch.integrate` and `demo_init`, `verify`
  (gates, autofix, acceptance), `guard`, `archlint`, `engines`, `config`, `task`. The
  worker engine `studio-14b` is `local-14b-arch` without the repo map, as in ChatBook.
- **Changed, backward-compatible:**
  - `run_task(..., run_id=None)`: the studio picks the id first, so it can follow
    `runs/<id>` live;
  - `integrate()` returns the integration branch, or None. It used to return a bool, and
    every caller only tests truthiness.
- **New:**
  - `frames/webapp` + `frames/webapp.toml`: the frame and its harness target. Its autofix
    starts with `tools/restore_contracts.py`, which puts a deleted or misplaced CONTRACT back
    on top. `Project.update_frame()` brings an existing project's frame files up to date on
    start, committed only if the frame's gates pass;
  - `swarm/studio/`:
    - `plan.py`: the plan model, checks and code generation;
    - `chief.py`: the Ollama planner and `FilePlanner`;
    - `project.py`: state, the job thread, the build loop and review;
    - `server.py`: the API, the event stream and the token;
    - `preview.py`;
    - `app.py`: the window;
    - `static/`: the UI;
  - `[studio]` in `swarm.toml`;
  - `swarm studio`.

## Project layout (`work/studio/<name>/`, git-ignored)

- `app/`: the app's git repo; `main` holds only reviewed work.
- `tasks/`: generated tasks and hidden tests, outside the repo.
- `runs/` and `worktrees/`: the harness's own.
- `logs/<task>.log`, `state.json`, `plan.json`, `plan.md`, `preview.log`.

## UI (one page, three panes)

- **Chat:** the owner's requests and the chief's replies. Plan messages carry Approve.
  During a build, chat notes are queued and planned when it ends.
- **Plan / Tasks:**
  - **Plan:** the plan artifact: routes, data, the example the worker sees, the hidden
    checks (folded), the page sections, and any problems.
  - **Tasks:** status, attempt n/4 and time per task. Each task has:
    - **Log:** live; harness lines plus the model's transcript;
    - **Diff:** base to commit for passed work, else the latest attempt;
    - **Attempts:** gate chips, and prompt, feedback, gates and model transcript per attempt.
- **Preview:** an iframe of the app served from `main`, reloaded after each merge. Sections
  whose routes are still stubs show "not built yet".

## Security

- **The server:**
  - binds 127.0.0.1 only, with an exclusive bind on Windows;
  - every `/api/` call needs the session token (compared as bytes, so a forged token gets a
    plain 403) and a `Host` header naming the server, so a web page or a DNS-rebinding
    attack can't drive it;
  - static paths are checked before the filesystem is touched (on Windows, `//host/share`
    would otherwise open a network share).
- **The page** uses `textContent` only.
- **The worker** runs exactly as in the harness: scrubbed environment, guard, and the Docker
  sandbox if chosen (`[studio] sandbox = "docker"` or `swarm --sandbox docker studio`).
- **The preview** runs the generated app with the same scrubbed environment as the gates
  (an allow-list, with git credentials and remotes off), as your user, on the host.

## The first real run (2026-11-02)

One chat message, then the local 14B chief and worker on the GTX 1080 Ti:
- **Plan:** about 3 min, 0 problems.
- **01-todos:** passed on attempt 1.
- **02-todo-edit:** failed all 4 attempts, although its hidden tests passed from attempt 1:
  - attempt 1: an unused variable and a missing return;
  - attempts 2 to 4: the model deleted the CONTRACT docstring, then kept restoring it
    *below the imports*, where Python no longer sees it as the docstring.
- **The fix:** ChatBook's rule, fix the inputs and never the model's code: the restore
  autofix and a frame update. The retry then passed on attempt 1.
- **03-todo-stats:** passed on attempt 1.

Screenshots and timings are in [`studio-demo/`](studio-demo/README.md).

## Review (2026-11-02)

A multi-agent review covered the whole branch:
- 6 reviewers: build loop, plan and codegen, security, harness integration, frontend, frame;
- 2 skeptics per finding, with a third on a split vote.

It confirmed 23 problems: 2 high, 9 medium and 12 low. All are fixed, most with a
regression test in `tests/test_studio_review.py` or the frame's tests.
- **The worst:**
  - approving a plan whose stubs failed the gates wedged the project; approve now goes
    through an "applying" status and rolls back;
  - the chief reused old hidden tests after an earlier feature changed.
- **Others:**
  - the preview ran model code with the full environment;
  - `--sandbox` was ignored by the studio;
  - stubs could fail the frame's line-length gate after approval;
  - a reply given as text made a hidden test impossible to pass;
  - unsynchronized writes of `state.json` could kill the job thread.

## Limits of the MVP

- **The page is declarative** (form, list, values). The worker writes only backend features.
  UI tasks written by the model would need a headless DOM runner for hidden tests, as
  ChatBook's `uirun.js` was.
- **Data is in-memory.** The preview's data resets when it restarts after each merge.
- **Pause takes effect between tasks.** A running attempt isn't killed.
- **Built features are never re-planned.** Additions only.
- **No multi-project UI.** Pick the project on the command line.
